# 技术报告：企业网关与自定义模型通道上下文处理机制与实测数据

> **取证对象**：Antigravity 桌面端推理引擎 `/opt/Antigravity/resources/bin/language_server`（`antigravity 2.29.1-1`，`Built at CL: 1015941558`，Linux x86-64，`SHA256: c666de77661e557a893ca7a30d9f4b280857b1870d357b07b9fb761730edfc26`）。
> **测试通道**：企业网关模式（`~/.antigravity/settings.json` 配置 `gateway` + `models.listSource`，或 `AGY_LLM_GATEWAY_*` 环境变量；`wireProtocol: "openai"`）。
> **覆盖模型**：`<gateway>/gemini-3.8-flash-high`（`MODEL_PLACEHOLDER_M340`）、`<gateway>/gemini-4-argon-high`（`MODEL_PLACEHOLDER_M363`）、`<gateway>/deepseek-v4.1-flash-1017`（`MODEL_PLACEHOLDER_M345`）。（注：实验环境中 `<gateway>` 为 13 字符网关前缀。）
> **通俗导读**：如需快速了解核心结论与配置原则，请参阅 [《原理与使用指南》](overview-and-guide.md)。

## 1. 核心结论

1. **桌面端企业网关模式默认绕开 `256,000` 钳位，实测默认预算高达 `872,000`（原生通道未修补时的 3.406 倍），无需二进制补丁。**
   桌面端将网关模型的 `apiProvider` 标记为 `API_PROVIDER_OPENAI_VERTEX`（枚举值 `31`）。在 `utils.GetCheckpointConfig`（`0x65154c0`）中，仅 `apiProvider` 为 `3`、`24`、`26` 的模型进入 `min(x, 256000)` 分支，网关模型在 `0x6515508` 处直接跳过该钳位。
2. **本地预算由网关模型目录容量参数按确定公式实时算出，修改目录即可免补丁调整本地预算：**
   $$\text{MaxTokenLimit} = \max\big(0,\ \text{MaxTokens} - \max(40000,\ \text{MaxOutputTokens})\big)$$
   实验目录中三个目标模型均声明 `maxTokens = 1,000,000`、`maxOutputTokens = 128,000`，代入得 `872,000`（与 SQLite 全部生成行 `max_context_tokens = 872000` 完全一致）。对照实验中将自建目录服务的 `maxTokens` 改为 `2,000,000` 后，数据库 `maxctx` 精确变为 **`1,872,000`**；同目录另一条目 `<gateway-alt>/gemini-4-argon`（`1,048,576 / 65,536`）实测 `maxctx` 精确为 **`983,040`**。
3. **上下文压缩依然完全由客户端本地发起；发往网关的 180 个 HTTP 请求体中压缩控制字段 0 命中。**
   客户端在 `hooks.checkpointNeeded`（`0x6876420`）判定装不下预算后，主动向网关发送一条 `max_completion_tokens = 16384`（常规主请求为 `128000`）的独立摘要请求，将生成的总结写入本地 SQLite `steps` 表（`step_type = 23`），随后的主请求体积从约 **`3.49 MB`** 骤降至 **`49.7 KB–52.8 KB`**（缩减 **98.5%–98.6%**）。
4. **主对话路径对单条用户输入存在约 `192 KB` 的独立截断机制。**
   `config.defaultConversationalCascadeConfig`（`0x669219c`）将 `TrajectoryConversionConfig.MaxTokensPerUserInputStep`（偏移 `+0x78`）默认设为 `64,000`（`0xfa00`），配合 `×3` 字节换算（`0x6f1ab7e`），将主生成请求中单条 700 KiB 用户文本截断至 `192,025` 字符并附注 `<truncated 525349 bytes>`。

## 2. 企业网关通道的五步请求处理链路

### 步骤 1：通道配置加载（`admincontrols` 包）

引擎支持两条网关配置途径（通过 `LoadEffectiveSettings` `0x6766be0` → `MergeSettings` `0x6765340` → `mergeGateway` `0x6765e60` 合并）：
- **配置文件路径**：用户级 `~/.antigravity/settings.json`（`defaultUserSettingsPath` `0x6763b80`）与系统管理员级 `/etc/antigravity/admin_settings.json`（`0x6763a80`）。
- **环境变量覆盖（`admincontrols.ParseEnvOverrides`，`0x6764900`）**：支持 `AGY_LLM_GATEWAY_URL`、`AGY_LLM_GATEWAY_WIRE_PROTOCOL`（`"openai"` 或 `"genai"`）、`AGY_LLM_GATEWAY_API_KEY`、`AGY_LLM_GATEWAY_HEADERS`、`AGY_LLM_GATEWAY_CA_CERT`、`AGY_LLM_GATEWAY_MODELS`、`AGY_LLM_GATEWAY_TIER_PRO` / `_TIER_FLASH` / `_TIER_FLASH_LITE`、`AGY_LLM_GATEWAY_PROXY_URL` 共 10 项（命令行版 `agy` 的 `GOOGLE_GEMINI_BASE_URL` 在桌面端中不存在）。

### 步骤 2：四级模型目录发现（Tier 1–Tier 4）与协议路由

`gateway.(*AuthProvider).GetModelCatalog`（`0x791e760`）按四级优先级解析可用模型：
1. **Tier 1**：管理员配置中的内联 `models.list`
2. **Tier 2**：远端目录 URL（`settings.json` 中的 `models.listSource`；本实验环境命中此级）
3. **Tier 3**：向网关端点自动探测（`fetchGatewayDiscoveredModels` `0x79225a0`）
4. **Tier 4**：引擎内置兜底默认目录

当走 Tier 3 自动探测与 `StreamGenerateContentFromGateway`（`0x6e6f080`）发送生成请求时，HTTP 路径由 `wireProtocol` 与网关 Base URL 后缀共同决定：

| `wireProtocol` 配置 | Base URL 结尾 | Tier 3 目录探测路径 | 流式生成请求路径 |
|---|---|---|---|
| `"openai"`（`.rodata 0x46277fb`） | `/v1` | `/models` | `/chat/completions` |
| `"openai"` | 其他 | `/v1/models` | `/v1/chat/completions` |
| `"genai"`（`.rodata 0x461a819`） | `/v1beta` 或 `/v1` | `/models?pageSize=1000` | `:streamGenerateContent?alt=sse` |
| `"genai"` | 其他 | 先试 `/v1beta/models?pageSize=1000`，再退 `/v1/models` | `:streamGenerateContent?alt=sse` |

### 步骤 3：`CheckpointConfig` 推导与 `256,000` 钳位绕行（反汇编证据）

在 `utils.GetCheckpointConfig`（`0x65154c0`）中：

```asm
65154f7: mov  edx, DWORD PTR [rcx+0x30]   ; edx = ModelInfo.ApiProvider
65154fa: cmp  edx, 0x3                    ; 3  = API_PROVIDER_GOOGLE_VERTEX
65154fd: je   651550e                     ; -> 进入 min(x, 256000) 钳位分支
6515500: cmp  edx, 0x18                   ; 24 = API_PROVIDER_GOOGLE_GEMINI
6515503: je   651550e                     ; -> 进入 min(x, 256000) 钳位分支
6515505: cmp  edx, 0x1a                   ; 26 = API_PROVIDER_ANTHROPIC_VERTEX
6515508: jne  6515851                     ; ★ 网关模型 provider == 31 (0x1f)，直接跳至 0x6515851！
...
6515942: call 6515140                     ; 调用 utils.GetDefaultCheckpointConfigForModel
6515954: cmp  DWORD PTR [rdx+0x14], 0x0   ; ModelInfo.MaxTokens <= 0 ?
6515958: jg   6515961                     ; MaxTokens > 0 时直接返回算出的预算，不做 256K 钳位！
651595a: mov  DWORD PTR [rax+0xc], 0x3e800 ; 仅当目录未提供正数 MaxTokens 时兜底填 256,000
```

而在 `utils.GetDefaultCheckpointConfigForModel`（`0x6515140`）中，减法公式逐指令清晰可见：

```asm
651516a: movsxd rdx, DWORD PTR [rcx+0x14] ; rdx = ModelInfo.MaxTokens (1,000,000)
651516e: movsxd rsi, DWORD PTR [rcx+0x70] ; rsi = ModelInfo.MaxOutputTokens (128,000)
6515172: cmp    rsi, 0x9c40               ; 与 40,000 比较
6515179: mov    edi, 0x9c40
651517e: cmovg  rdi, rsi                  ; rdi = max(40000, MaxOutputTokens) = 128,000
6515182: cmp    rdx, rdi
6515185: jg     651518b
6515187: xor    edx, edx
6515189: jmp    651518e
651518b: sub    rdx, rdi                  ; rdx = 1,000,000 - 128,000 = 872,000
...
6515370: mov    DWORD PTR [rax+0xc], ecx  ; 写入 CheckpointConfig.MaxTokenLimit (+0xc)
```

### 步骤 4：OpenAI 格式流式请求结构与摘要指纹

当 `isOpenAIGateway`（`0x6e6eea0`，判据为 `provider == 31` 或 `wireProtocol == "openai"`）成立时，引擎向网关发送 `POST /v1/chat/completions`：
- **常规主请求顶层恒为 7 个键**：`model, messages, stream, stream_options, reasoning_effort, max_completion_tokens, tools`（另有无 `tools` 与 `max_completion_tokens` 的 5 键会话标题生成请求）。
- **全部 180 个捕获请求体全树键扫描**：`checkpoint_config`、`max_token_limit`、`context_window`、`autoCompact` 等关键词命中数均为 **0**。
- **独立摘要请求的协议识别指纹**：网关协议无 `requestType` 字段，但常规主请求的 `max_completion_tokens` 恒等于目录 `maxOutputTokens`（`128000`），而独立摘要请求恒降为 **`16384`**（10/10 摘要尝试严格对应）。

### 步骤 5：前置钩子拦截并发起本地压缩

每轮主请求前，`NewContextSummaryHook.func1`（`0x70577a0`）调用 `hooks.checkpointNeeded`（`0x6876420`）；当遇到 `ErrTruncation`（`0x68765a6`）时，引擎记录日志 `"Checkpointing: no messages fit the executor budget, compacting"`，调用 `hooks.generateContextSummary`（`0x6876820`）发送 `max_completion_tokens = 16384` 的摘要请求，写入本地 SQLite `steps` 表 `step_type = 23`，随后发出瘦身后的主请求。

**核心观测结论**：
1. **压缩前末轮请求字节高度一致**：三个模型末轮成功主请求字节数极差仅 **`316 B`（`0.009%`）**，而服务端分词器统计的 `prompt_tokens` 相差 **`93,414` tokens（`14.9%`）**，且网关对 `3.49 MB`（`62.5 万–71.8 万` tokens）请求全部正常返回 `HTTP 200`。
2. **压缩后瘦身请求 `6.28%` 体积差的字节级归因**：拆解 `#113`（Flash）、`#114`（Argon）、`#75`（DeepSeek）四个组成部分：
   - `system` 提示词长度三者均为 **`16,306 B`**（因内嵌模型名不同，文本哈希不同）；
   - 工具定义与 JSON 包装开销分别为 `19,301`、`19,278`、`19,317 B`（极差仅 `39 B`）；
   - `user` 消息固定非摘要模板三者均为 **`11,141 B`**；
   - 模型生成的摘要正文长度分别为 **`2,981 B`**、**`3,131 B`**、**`6,086 B`**——DeepSeek 与 Flash 的总体积差 `3,121 B` 中有 `3,105 B`（**99.49%**）来自 DeepSeek 生成的摘要文本更长，而非客户端压缩框架存在差异。
3. **Argon 跨运行落库与记录代理缓冲辨析**：Argon 主运行第 18 轮曾发出 5 次摘要尝试（`#91, #94, #99, #100, #103`），客户端均报 `timeout awaiting response headers`（其中实验用的本地记录代理在收完整个上游流式响应后才向引擎转发响应头，当 `#99` 生成了 `194,937` 字符超长响应时加剧了客户端等待响应头超时）。随后复用同一会话 ID 续跑时，`#112` 生成 `3,131` 字符摘要并成功写入 `steps idx=40`（摘要正文 SHA256 与数据库 `30→5` 载荷完全一致）。
4. **`steps` 表 `user_config` 二进制核验**：对 4 个实验数据库全部 83 条用户输入步骤（`step_type = 14`）解码 `CortexStepUserInput.user_config`（路径 `19→12`），均仅含 13 字节的 `planner_config`（所选模型枚举），子字段 `2`（`checkpoint_config`）在 83/83 条记录中均为空，证实 `872,000` 预算由引擎在运行期根据目录动态推导而非由前端请求注入。

## 4. 可配置性矩阵与配置安全原则

### 4.1 潜在配置入口核验汇总

| 配置入口 | 验证方法 | 结论 |
|---|---|---|
| **网关模型目录 `maxTokens` 字段** | 受控对照实验（目录设为 `2,000,000`，`maxOutputTokens = 128,000`） | **直接生效**：SQLite `maxctx` 实测变为 **`1,872,000`**（会话 `32cd9627…`）。 |
| **网关模型目录 `maxOutputTokens` 字段** | 反汇编 `0x651517e` + 目录条目旁证（`1,048,576 - 65,536`） | **反向调节生效**：当 `> 40,000` 时调低输出预留可增加输入预算（会话 `1c09eca9…` 实测 `maxctx = 983,040`）。 |
| **`/etc/antigravity/admin_settings.json`** | 反汇编 `LoadEffectiveSettings`（Tier 1 目录优先级） | 可通过管理员内联 `models.list` 指定 `maxTokens` / `maxOutputTokens`。 |
| **`AGY_LLM_GATEWAY_*` 环境变量** | `.text` 段引用扫描 | 无直接预算数值变量，但改变网关 URL 或目录源会间接改变目录参数。 |
| **`~/.antigravity/settings.json` 其他键** | Go 结构体 `ModelEntry` JSON Tag 解析 | 仅支持模型元数据字段，无 `contextWindow` 或 `maxTokenLimit` 键。 |

### 4.2 调整网关目录容量的安全原则

1. **客户端预算不等于上游物理容量**：调高网关目录中的 `maxTokens` 仅推迟本地客户端发起摘要，不会扩容上游模型的真实上下文窗口。目录声明的 `maxTokens` 不应超过上游模型经验证的真实物理容量，且应预留充足的 `maxOutputTokens` 与工具定义开销。
2. **有符号 32 位整数边界**：`ModelInfo.MaxTokens` 在引擎内部按有符号 32 位整数（`int32`）读取，切勿填入超出 `int32` 正数范围的极大值（溢出为负数将触发 `<= 0` 的 `256,000` 兜底分支）。

## 5. 触发谓词边界分析：小步爬升反例实验（`creepDS3`）

在主实验中，三个模型的第 17 轮成功请求体均停在约 `3,494 KB`（`3,494,051 / 4 = 873,513 ≈ 872,000`）。为检验“是否只要 `请求体原始字节 ÷ 4 >= 872,000` 或 `DB est >= 某固定值` 即触发压缩”，设计了针对 DeepSeek 模型的小步爬升反例实验（会话 `59287c7c…`：先发送 16 条约 192 KB 消息，再连续追加 26 条 20 KB 小消息，共 84 条 `messages`）：

| 对比维度 | 主实验第 17 轮（`#70`，进入下一轮即触发压缩） | 小步爬升实验末轮（`#198`，**未触发压缩**） | 含义 |
|---|---:|---:|---|
| HTTP 请求体总字节 | `3,494,143 B` | **`3,640,395 B`** | 高出 `146,252 B` 仍未触发压缩 |
| 消息纯文本总字节 | `3,473,674 B` | **`3,617,264 B`** | 高出 `143,590 B` 仍未触发压缩 |
| 本地数据库 `DB est` 峰值 | `1,164,101` | **`1,212,010`** | 高出 `47,909` 仍未触发压缩 |
| `step_type = 23` 压缩次数 | 下一轮（候选输入约 `3.686 MB`）触发 | **`0` 次** | 证伪简单的 `原始字节 ÷ 4 >= 872,000` 预测器 |

**严谨边界结论**：
- 该反例确凿证伪了“已发送请求体 ÷ 4 ≥ `872,000`”及“`DB est` 固定阈值”两个简化假说。
- 由于钩子 `hooks.checkpointNeeded` 面对的第 18 轮待发输入已包含新提交的 `192 KB` 消息（总候选规模约 `3.686 MB` > `3.640 MB`），且 `0x6876574: call r12` 为接口动态分发，触发瞬间的精确内部算式（究竟是“最新单条消息无法塞入剩余空间”还是位于 `[3.64 MB, 3.68 MB]` 区间的内部序列化总量阈值）作为开放技术边界保留，不影响配置预算 `872,000` 及本地发起压缩的核心结论。

## 6. 延伸分析：同一企业网关接入其他客户端时的边界

由于 `872,000` 预算推导与单条消息 `192 KB` 截断均位于 Antigravity 桌面端 `language_server` 本地二进制内，当将同一企业网关接入其他 AI 编程客户端时：
1. Antigravity 客户端层的本地压缩预算与 `192 KB` 单步截断均不再介入。
2. 实际上下文边界由以下三方共同决定：
   - **新客户端自身的上下文裁剪或摘要策略**；
   - **网关实例转发配置**：如 HTTP 请求体大小上限（本实验已验证目标网关至少可正常流式转发 `3.64 MB` 请求体）与流式响应超时设置；
   - **上游模型真实物理窗口与内容安全过滤**（Content Safety Filter 独立于长度限制存在）。
